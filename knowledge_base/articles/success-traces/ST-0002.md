## Failed Attempts Before Success
> These attempts immediately preceded the successful workflow and provide critical context.

### Attempt 1 (A-000002-FAIL-1)
**Technique:** on-device unpack-dir harvesting
**Tools:** TR-0001
**Action:** Search /data/data and /sdcard for ark_payload_*.dex or any decrypted dex after launching the app
**Result:** FAILED
**Failure Reason:** The loader uses InMemoryDexClassLoader and never writes dex to disk. File count was 4 before and 4 after launch.
**Observation:** Zero dex on disk while four [anon:dalvik-DEX data] regions existed in memory.
**Why It Matters:** This is the documented 360 jiagu path in the KB, so an agent following the existing playbook would have returned empty. Abandoned after one cheap check rather than a long search.
### Attempt 2 (A-000002-FAIL-2)
**Technique:** column-frequency XOR key recovery on payload blobs 2-4
**Tools:** TR-0004, TR-0011
**Action:** Recover per-column most-frequent-byte keys at all 64 phase rotations and test each for a DEX header
**Result:** FAILED
**Failure Reason:** Blob plaintext is not zero-dominated, so per-column mode does not recover the key. Autocorrelation still peaked at lag 64 (33.69%), proving a 64-byte key exists but not derivable this way.
**Observation:** All 64 rotations failed to yield magic dex\n035\0.
**Why It Matters:** This is what motivated the switch to dynamic memory harvesting, and it bounds the offline method: it works for zero-dominated blobs only.
### Attempt 3 (A-000002-FAIL-3)
**Technique:** standard compression probe on the secondary blob
**Tools:** TR-0011
**Action:** Try zlib, gzip, lzma, bz2 and zstd on the encrypted payload region
**Result:** FAILED
**Failure Reason:** All rejected; the payload is a custom cipher, not a compressed stream. (zstandard module also unavailable.)
**Observation:** No magic bytes for any supported codec.
**Why It Matters:** Confirms the payload is genuinely encrypted rather than merely packed, matching the absence of AES/ChaCha/MD5/SHA constants in libchikoStub.so.
