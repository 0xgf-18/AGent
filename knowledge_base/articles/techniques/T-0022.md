# Technique T-0022: Repeating-key XOR period detection via harmonic-comb autocorrelation

## This Article Answers

- "When does technique T-0022 apply?"

## Key Takeaways
- [PROBLEM] Recovering a repeating-key XOR stream requires knowing the key length before you can build a key table, and the standard index-of-coincidence shortcut ('find the lag with the highest autocorrelation') gives the wrong answer for the most obvious reason in the world: a key of period P correlates strongly at P, 2P, 3P and every other multiple, so the largest peak is almost never the fundamental period, and the runner-up is nearly as tall. Any acceptance test phrased as 'the peak must be unique' or 'the second-best lag must be much lower' therefore rejects correct recoveries outright. This technique derives the fundamental period from the harmonic comb and separates signal from noise with the correct statistic, so a real period-64 key is recovered and random data is rejected.

- [VERIFICATION] structural + content + parser >=3 categories, zero FAIL
- [CONFIDENCE] 0.75 (CANDIDATE)

## Problem Statement
- Protection class addressed: `static-analysis`
- Why standard approaches fail: —
- Applicable when: autocorrelation (match-index) of the payload is strongly elevated at many lags rather than flat; the elevated lags form an arithmetic progression sharing a common divisor; a single lag dominates and no other lag is close to it; payload length is a large multiple of the candidate period

## Workflow

### Step 1: Step 1
**Observation:** Packed APK in hand; the encrypted blob may be appended past the DEX data section or stored as an asset
**Action:** Isolate the encrypted bytes. For an appended payload, read data_off (0x6C) and data_size (0x68) from the shell classes.dex and take everything after data_off+data_size; confirm the gap is large (>= 1 MB) to know you are not slicing a normal dex
**Tool:** TR-0001
**Expected Result:** A contiguous byte range that is the encrypted payload and nothing else
**Success Indicator:** payload byte count recorded, and it is implausibly large for a dex data section
**Failure Mode:** Slicing a legitimate dex section yields a flat autocorrelation and you will wrongly conclude 'not periodic'
### Step 2: Step 2
**Observation:** Payload isolated
**Action:** Over a 200 KB sample, for each lag 1..512 count positions where byte[i] == byte[i+lag] and divide by the number of comparisons
**Tool:** TR-0001
**Expected Result:** A lag->score table; the noise floor for random data sits near 0.39%
**Success Indicator:** a table exists and the bulk of lags are near 0.39%
**Failure Mode:** Sampling too little makes the table noisy; a sample shorter than max_lag cannot be scored at all
### Step 3: Step 3
**Observation:** Lag table computed
**Action:** Let peak be the global maximum. Define 'elevated' as any lag scoring >= 40% of peak. The fundamental period is the SMALLEST elevated lag, not the largest
**Tool:** TR-0001
**Expected Result:** A candidate period P
**Success Indicator:** on the reference sample this yields 64 while the global maximum also happens to be 64 but the harmonics 128-512 score 48-49.6%, proving the maximum is not a safe choice in general
**Failure Mode:** Taking argmax returns a harmonic whenever the sample is short enough for a multiple to edge out the fundamental
### Step 4: Step 4
**Observation:** Candidate period P extracted
**Action:** Assert that EVERY elevated lag is an integer multiple of P. If any elevated lag is not, there is no single period and the payload is not a simple repeating-key XOR
**Tool:** TR-0001
**Expected Result:** All elevated lags are multiples of P
**Success Indicator:** on the reference sample the elevated set is exactly {64,128,192,256,320,384,448,512} = 1P..8P
**Failure Mode:** A payload with two unrelated periods, or a block cipher, fails here, which is the correct outcome
### Step 5: Step 5
**Observation:** Comb confirmed
**Action:** Compute the maximum score over lags that are NOT multiples of P. This number, not the median and not the second-best overall, is the noise floor you must compare the peak against
**Tool:** TR-0001
**Expected Result:** noise_max well below peak
**Success Indicator:** reference sample: noise floor 1.85% (median 0.39%) against a 50.85% peak
**Failure Mode:** Using the median understates the floor and can mask a partially-periodic payload; using the overall runner-up is meaningless because harmonics are legitimately near-peak
### Step 6: Step 6
**Observation:** Period P established and comb verified
**Action:** For each column i in 0..P-1, take cipher[i::P] and set key[i] to its most frequent byte. This assumes the dominant plaintext byte in each column is 0x00, which holds for dex data sections and code sections
**Tool:** TR-0001
**Expected Result:** A P-byte key candidate
**Success Indicator:** decrypting with it yields a blob whose dex magic, file_size, adler32 and sha1 all agree
**Failure Mode:** If the plaintext is not zero-dominated the mode picks the wrong byte per column and every checksum fails; this is expected on high-entropy regions and is the signal to stop and use a memory carve instead
### Step 7: Step 7
**Observation:** Key candidate built
**Action:** Decrypt and validate as a dex: magic dex\n, header_size 0x70, endian 0x12345678, file_size equal to the blob length, adler32 over bytes[12:] equal to u32 at 0x08, and sha1 over bytes[32:] equal to bytes[12:32]
**Tool:** TR-0001
**Expected Result:** A dex that passes BOTH adler32 and sha1
**Success Indicator:** both checksums pass simultaneously on the same bytes
**Failure Mode:** adler32 passing while sha1 fails means truncation or misalignment, not a correct key; never accept adler32 alone

## Decision Points
| Decision Point | Condition | If True | If False |
|---|---|---|---|
| DP1 | global max autocorrelation below 30% | no periodicity at all - the payload is not a simple repeating-key XOR; stop and use a runtime memory carve (T-0010) | periodicity exists, continue to the comb test |
| DP2 | smallest elevated lag P, but some other elevated lag is not a multiple of P | not a single repeating key - reject the offline path rather than guessing which structure to trust | the comb is intact, P is the period |
| DP3 | max non-multiple lag exceeds 50% of the peak | noise floor too close to signal to claim a period; treat as unproven | the peak is isolated and the period is credible |
| DP4 | key built by column mode decrypts to something failing adler32 or sha1 | plaintext is not zero-dominated (compressed or high-entropy blob) - the offline key does not apply to this blob, use a device memory carve | the key is confirmed; proceed to split the stream on each blob's own file_size |

## Success Indicators
- the set of elevated lags is exactly {P, 2P, 3P, ...} with no strays
- max non-multiple-of-P lag is far below the peak (reference: 1.85% vs 50.85%)
- the recovered key reproduces a dex whose adler32 AND sha1 both validate
- the recovered key is byte-identical across independent runs on the same input

## Limitations
- column-mode key recovery only works when the dominant plaintext byte per column is 0x00; on compressed or otherwise high-entropy blobs it fails, and the correct response is to stop rather than to try harder
- detects only repeating-key XOR at the sampled lag range; a period longer than max_lag, or a stream/block cipher, will read as noise
- the comb test cannot distinguish a period-P key from a period-P key applied to data that is itself periodic
- the 40%-of-peak and 50%-of-peak thresholds are empirical choices from one payload; they are not derived and may need adjustment on a noisier sample
- verified on ONE payload (Chiko/NeoArk, 10,160,347 B). The negative control used synthetic random bytes, not a real second cipher, so the thresholds are under-sampled across ciphers
