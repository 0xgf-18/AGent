# Technique T-0021: Packer storage-model detection (disk-harvest vs memory-carve router)

## This Article Answers
- "How do I packer storage-model detection (disk-harvest vs memory-carve router)?"
- "When does technique T-0021 apply?"
- "What are the prerequisites for T-0021?"

## Key Takeaways
- [PROBLEM] Two competing on-device unpacking techniques exist and they are mutually exclusive, but nothing tells you which one to reach for: T-0019 harvests decrypted dex from the on-disk unpack directory (no_backup/dex_unpack), while T-0010 carves dex out of live process memory (/proc/<pid>/maps + /proc/<pid>/mem). Picking wrong means hours of fruitless searching - on Chiko/NeoArk the data directory is byte-identical before and after launch, so T-0019 finds nothing at all, yet the app has four full dex payloads sitting in memory. This technique cheaply determines the packer's storage model and routes to the correct technique before any harvesting begins.
- [PREREQUISITES] tools TR-0001, TR-0002, TR-0009, TR-0011; root=True; env rooted device or emulator (su), adb in device state, app launchable on the device
- [WORKFLOW] Count files under /data/data/<pkg> as ro -> Force-stop the app, clear logcat, launch -> Re-count and re-list /data/data/<pkg> as -> Corroborate with a static and a dynamic  -> Route accordingly - memory-resident => e
- [VERIFICATION] REPRODUCIBILITY (file-count diff is repeatable) + PARSER (dex adler32/sha1 via verify_result.py) + CONTENT (target app classes present) + DOWNSTREAM (rebuilt APK installs and cold-launches) + STRUCTURAL (zero packer residue)
- [CONFIDENCE] 0.7 (CANDIDATE)

## Problem Statement
- Protection class addressed: `dynamic-dump`
- Why standard approaches fail: —
- Applicable when: /data/data/<pkg> file count IDENTICAL before and after app launch; [anon:dalvik-DEX data] regions present in /proc/<pid>/maps but no dex on disk; loader binary contains the string 'dalvik/system/InMemoryDexClassLoader'; loader string 'ark_payload_%d.dex' or 'ark_code_cache' present but corresponding files absent on disk; anon DEX region sizes roughly match the size of the encrypted payload appended to the APK; no_backup/dex_unpack or similar unpack dir exists and is populated

## Workflow

### Step 1: Step 1
**Observation:** Packed APK in hand; need to know whether dex will land on disk or only in memory
**Action:** Count files under /data/data/<pkg> as root BEFORE launching the app, to establish a baseline
**Tool:** TR-0001
**Expected Result:** A small integer file count and a saved list of paths
**Success Indicator:** baseline count recorded; note whether any dex-like file already exists
**Failure Mode:** —
### Step 2: Step 2
**Observation:** Baseline captured; the app has not run yet
**Action:** Force-stop the app, clear logcat, launch the main activity, wait ~12 s for attachBaseContext to complete
**Tool:** TR-0001
**Expected Result:** Process alive; unpack trigger (Application.attachBaseContext) has executed
**Success Indicator:** pidof returns a pid; logcat shows the activity START
**Failure Mode:** —
### Step 3: Step 3
**Observation:** App has run long enough to unpack; re-inventory the data directory
**Action:** Re-count and re-list /data/data/<pkg> as root, then DIFF against the baseline
**Tool:** TR-0001
**Expected Result:** Either new files (unpack dir appeared) or an identical list
**Success Indicator:** diff computed; identical count means the loader writes nothing to disk
**Failure Mode:** —
### Step 4: Step 4
**Observation:** Storage model still ambiguous from the file diff alone
**Action:** Corroborate with a static and a dynamic signal: grep the loader .so for InMemoryDexClassLoader / ark_payload strings, and check /proc/<pid>/maps for [anon:dalvik-DEX data] regions with their addresses and sizes
**Tool:** TR-0001
**Expected Result:** InMemoryDexClassLoader present AND anon DEX regions present AND no new files => memory-resident
**Success Indicator:** all three signals agree; region sizes give you the expected blob count and sizes
**Failure Mode:** —
### Step 5: Step 5
**Observation:** Verdict reached: memory-resident (Chiko/NeoArk) or disk-harvestable (PokeGuard-style)
**Action:** Route accordingly - memory-resident => execute T-0010 (dump each anon DEX region from /proc/<pid>/mem with dd iflag=skip_bytes,count_bytes, carve on the dex header, require adler32 AND sha1); disk-harvestable => execute T-0019 (copy the unpack dir, then validate each dex). Record which branch was taken and why.
**Tool:** TR-0011
**Expected Result:** Checksum-valid dex from the correct source, and a written record of the branch decision
**Success Indicator:** every accepted dex passes adler32 and sha1; the routing decision is documented with the file-count evidence
**Failure Mode:** —

## Decision Points
| Decision Point | Condition | If True | If False |
|---|---|---|---|
| DP1 | /data/data file count IDENTICAL pre- and post-launch | memory-resident -> use T-0010 (/proc/<pid>/mem anon-DEX carving); abandon T-0019 immediately | disk-harvestable -> use T-0019 (copy the unpack dir), with T-0010 as fallback |
| DP2 | loader .so contains 'dalvik/system/InMemoryDexClassLoader' | predict memory-resident before launching; pre-commit to T-0010 | still run the file-count diff - the string is a strong hint, not proof |
| DP3 | no [anon:dalvik-DEX data] in /proc/<pid>/maps but payload is definitely present | app not yet unpacked (attachBaseContext has not run) OR payload loaded another way - relaunch and wait, then re-check maps before assuming failure | proceed with T-0010 using the regions found |
| DP4 | carved blob passes adler32 but fails sha1 | truncated or misaligned region - re-dump with the exact region size from maps, do not accept | both match => provably a complete dex, accept |

## Success Indicators
- file count before launch == file count after launch, with the diff shown explicitly
- [anon:dalvik-DEX data] regions enumerated from /proc/<pid>/maps with addresses and sizes
- exactly one 'dex\n' magic per region, at offset 0
- adler32 (bytes[12:]) == u32@8 AND sha1(bytes[32:]) == bytes[12:32] for EVERY accepted dex
- anon DEX region sizes reconcile with the appended-payload size from static analysis
- routing branch recorded with the evidence that justified it

## Verification Method
5-category gate (PARSER/STRUCTURAL/CONTENT/REPRODUCIBILITY/DOWNSTREAM); the router itself is verified by REPRODUCIBILITY (the file-count diff is repeatable) and DOWNSTREAM (the routed technique produced an installable, runnable APK). VERIFIED_SUCCESS only at >=3 distinct categories with zero FAIL.

**Final Status:** COMMAND_SUCCESS vs VERIFIED_SUCCESS (only VERIFIED_SUCCESS counts for learning)

## Limitations
- requires root: the shell uid cannot read another uid's /proc/<pid>/mem, so this cannot run on an unrooted device
- the app must actually launch and attachBaseContext must run before the DEX regions are populated - a force-stopped or never-started app shows nothing
- the file-count diff detects the DISK-vs-MEMORY distinction, not whether the payload is additionally encrypted a second time or fetched from network
- region addresses are per-launch; a new launch needs a fresh maps read and fresh dd offsets
- an ARM-only APK needs ARM translation on an x86 emulator or the app will not run at all (separate failure mode - the app simply fails to start)
- proven on ONE packer family (Chiko/NeoArk) plus a PokeGuard-family negative; other in-memory packers untested (evidence: 1 APK)
