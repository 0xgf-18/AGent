### Why the 360 jiagu detection is wrong `[V]`
The whole verdict rested on one filename substring. Reading the file settles it:
```
$ unzip -p crackme.apk assets/libjiagu_mips.a
NeoArk fake 360 marker for tool identification only;
https://github.com/HSSkyBoy/Art-Jiagu
```
91 bytes, plain ASCII, no `PokeGuard` magic, no container. Cross-checks that also rule 360 jiagu out `[V]`:
- no `com.stub.StubApp` / `com.qihoo.util.*` anywhere — the application class is `b2al.encryp.vip`
- no `libSecShell.so`, no `vmInterpret`/`gVm` exports
- no `assets/ProtectV*.zip`
- `classes.dex` is 10 MB, not the ~44 KB shell described in [[wiki/packers/360-jiagu]]

**Generalisable lesson `[I]`:** `apk_fingerprint.py` packer detections whose `tool` is `entry-name heuristic` are filename substring matches and are `[AI Synthesis]`-grade until corroborated by magic bytes and payload structure. NeoArk appears to plant these markers deliberately, to make tool-chaining land on the wrong packer.

### The loader is memory-resident `[V]`
The decisive early check — data-dir file count across a launch:

| Moment | Files in `/data/data/com.mducdz.fakeping` | dex present |
|---|---|---|
| Before launch | 4 | no |
| 12 s after launch | **4 (unchanged)** | **no** |

The loader decrypts into memory via `InMemoryDexClassLoader` and writes **nothing** to disk. `libchikoStub.so` is mapped in-process and four `[anon:dalvik-DEX data]` regions exist `[V]`.

> This is why the KB's on-device unpack-dir harvest — the documented path for 360 jiagu — is a **dead end** for this packer. Diffing the file count before/after launch detects this in seconds `[I]`.

### Phase 2 — memory harvest, rooted device (EXP-0003) `[V]`
Four `[anon:dalvik-DEX data]` regions were dumped from `/proc/<pid>/mem` and carved on the dex header:

| r1 | `0x70154e83e000` | 9,303,180 B | valid | 6,292 | 68,694 | `1d8faf14…` |
| r2 | `0x7015a4cd0000` | 504,136 B | valid | 247 | 6,975 | `c468856c…` |

| r4 | `0x7018983eb000` | 105,656 B | valid | 48 | 1,533 | `e755352f…` |

All four passed **adler32 *and* sha1** — ART's own integrity fields — which is what makes a carved memory blob provably a complete dex rather than merely plausible-looking `[V]`.

**Cross-validation `[V]`**: r1's sha256 is **byte-identical** to Phase 1's offline-recovered dex#0. Two unrelated methods (statistical key recovery on the APK vs. process-memory harvesting) converging on the same bytes is far stronger than either result alone, and it retrospectively confirms the offline XOR key was correct.

Zero duplicate class definitions across the four dex, so they concatenate cleanly as multidex `[V]`.

## Open Questions / Unverified Claims
- `[U]` The trailing `04 00 00 00` matches the recovered blob count (4) exactly, so it is most likely a count — but its precise role is still unconfirmed
- `[U]` Only one sample of this packer family was studied. Whether the 64-byte key length and per-blob keying are stable across builds, or derived per-APK from a seed, is untested
- `[AI Synthesis]` The per-blob key is likely derived from a seed (APK signature, package name, or a `.rodata` constant) rather than being static. Reversing it would make the whole packer solvable with no device at all — the most valuable follow-up
