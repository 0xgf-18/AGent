## Observations
| Step | Observation | Significance |
|---|---|---|
| 1 | assets/libjiagu_mips.a is a 91-byte ASCII decoy: 'NeoArk fake 360 marker for tool identification only' | The entry-name heuristic in apk_fingerprint.py fires on the filename substring 'jiagu' and reports High confidence, which is a FALSE POSITIVE. Any detection sourced from 'entry-name heuristic' must be corroborated by magic bytes and payload structure before driving a technique chain. |
| 2 | data_off+data_size (0x3a4) is ~0.009% of file_size; the remaining 10,160,347 B is appended outside every DEX section | A 'valid' DEX header with a huge file_size but tiny data_size is a reliable static tell for append-payload packers. Adlersum/sha1 still validate over the whole file because the packer recomputes them, so verify_result.py parser PASSES on the shell -- a parser PASS alone does NOT mean the dex is unpacked. |
| 4 | 0 Java_* exports but JNI_OnLoad present, plus a format string 'ark_payload_%d.dex' | Dynamic RegisterNatives means the method table is not statically recoverable from dynsym; but the 'ark_payload_%d.dex' template tells us the loader writes decrypted dex to disk, confirming a file-based (not in-memory-only) unpacking path. |
| 5 | Autocorrelation spikes ONLY at multiples of 64, peaking at 50.85% | Distinguishes a short repeating XOR key from a stream cipher or block cipher. The 50% (not 100%) figure is exactly what plaintext-varied XOR gives, and rules out a constant-byte cipher. |
| 6 | Column-wise mode recovers all 64 key bytes; the first 8 decrypted bytes are a valid DEX magic and both adler32 and sha1 verify | For XOR-encrypted payloads whose plaintext contains long zero runs, statistical key recovery needs no device, no root, and no execution. Validating with adler32+sha1 makes the recovery cryptographically certain rather than probabilistic. |
| 7 | A 64-byte period persists in the tail (33.69%) but no rotation of the column-mode key yields a DEX header | Column-mode key recovery depends on the most frequent plaintext byte per column being 0x00. That holds for dex#0's data section but evidently not for the secondary blob, whose plaintext distribution is more uniform. Recovering that key needs either the algorithm from libchikoStub.so or a crib-drag with valid DEX header constraints. |

## Learning Extracted
- **What worked:** â€”
- **What didn't work:** â€”
- **Environment sensitivity:** None. Fully offline, host-only. This is the key advantage over the 360 jiagu dynamic-harvest path in [[wiki/packers/360-jiagu]], which needs a rooted device.
- **Tool version sensitivity:** verify_result.py writes UTF-8 JSON; PowerShell '>' redirection mangles it to UTF-16LE and UTF-8-BOM, which makes the gate read the file as corrupt. Write gate JSON from Python (encoding='utf-8') or use Out-File -Encoding utf8 then strip the BOM. Also: tool_discover.py reports aapt/dexdump/apksigner/zipalign as 'available' though they are NOT on PATH (they live in %LOCALAPPDATA%\Android\Sdk\build-tools\35.0.0) -- call them by full path.
- **New indicators discovered:** classes.dex with file_size >> data_off+data_size (appended payload), assets/*jiagu* that is a short ASCII decoy, not a container, string 'ark_payload_%d.dex' / 'ark_code_cache' in the loader .so, application class outside the app package (b2al.encryp.vip for com.mducdz.fakeping), u32 count == 4 in the last 4 bytes of the appended payload
- **Refined applicability for technique:** New packer family (Chiko/NeoArk) with no existing article. The 360 jiagu article's method is NOT applicable: this APK has no libSecShell.so, no PokeGuard container, no ProtectV*.zip, and the char-table decode step has no analogue. The correct first move is the appended-payload check, not container walking.
