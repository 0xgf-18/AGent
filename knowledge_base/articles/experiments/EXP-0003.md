## Key Takeaways
- [APPROACH] exploratory — Second phase of A-000002. EXP-0002 recovered only the primary 64-byte-XOR blob offline (a helper component). With a rooted emulator available, the remaining blobs were harvested by dumping [anon:dalvik-DEX data] regions from /proc/<pid>/mem -- the Chiko loader uses InMemoryDexClassLoader and writes NO dex to /data/data. Four checksum-valid dex recovered (6738 class_defs total) including the actual com.mducdz.fakeping business logic. Rebuilt into a signed, aligned, installable APK that cold-launches to MainActivity with no crash.
- [TOOLS] TR-0001, TR-0002, TR-0004, TR-0006, TR-0009, TR-0011
- [RESULT] SUCCESS (VERIFIED_SUCCESS)
- [LEARNING] When an append-payload packer resists offline key recovery, go dynamic: the loader keeps payloads in [anon:dalvik-DEX data] memory regions rather than writing to /data/data, so a FILE-SYSTEM harvest finds nothing (only 4 files, unchanged after launch). Dump /proc/<pid>/mem at the region addresses from /proc/<pid>/maps and carve on the dex header -- self-validating via adler32+sha1. The region dumped at 0x70154e83e000 hashed to exactly the dex recovered statically in EXP-0002, independently confirming the offline XOR key was correct.

## Observations
| Step | Observation | Significance |
|---|---|---|
| 4 | The app wrote ZERO dex to /data/data -- the data dir was byte-identical before and after launch (4 files) | The KB's on-device unpack-dir harvesting technique (T-0019), which is the documented path for 360 jiagu, is a dead end for Chiko/NeoArk. The loader's use of InMemoryDexClassLoader means there is nothing on disk to copy. Recognizing this early -- by checking the file count before and after launch -- is what redirected the work to memory dumping instead of wasting time on filesystem harvesting. |
| 5 | The 9,088 kB anon DEX region's size is within ~3 kB of the 9,303,180 B dex recovered offline in EXP-0002 | Size was enough to predict the mapping, which made the memory-dump plan concrete before any dumping. Region size is a reliable free signal for how many payload blobs to expect. |
| 8 | r1's sha256 from memory is byte-identical to the dex#0 recovered by the offline 64-byte XOR key | Two completely independent methods -- statistical key recovery on the APK and memory harvesting on a device -- converged on the same bytes. This is much stronger evidence than either alone: it proves the offline path generalizes, and it retrospectively validates EXP-0002's primary-blob result. |
| 10 | None of the 6,738 classes extends android.app.Application, yet the packed manifest pins android:name=b2al.encryp.vip | Packer-injected manifest attributes are the single most common cause of 'unpacked dex is perfect but the app won't start'. The check is cheap (list superclasses) and the fix is a one-attribute deletion. Missing this would have produced a crash-on-launch rebuild that looked like a failed unpack. |
| 11 | libchikoStub.so and the decoy asset assets/libjiagu_mips.a are the only packer-owned files; libfping.so belongs to the app | Distinguishing packer artifacts from legitimate app native libs is necessary for a clean rebuild. libfping.so was kept -- dropping it would have broken the app's own native code. The 'lib' in a Chiko APK is not automatically packer-owned. |
| 12 | Cold launch of the rebuild took 1455 ms and the crash buffer was empty | Runtime acceptance is the only verification that distinguishes a real unpack from a pile of valid-looking dex files. The unpacked build also skips the packer's runtime 10 MB decryption entirely. |

## Learning Extracted
- **What worked:** —
- **What didn't work:** —
- **Environment sensitivity:** Needs root (su) to read /proc/<pid>/mem for another uid, and needs ARM translation because the APK is arm64-v8a while the emulator is x86_64. MuMu provided both via KernelSU and ro.dalvik.vm.native.bridge=libnb.so. The app must be launched (or at least attachBaseContext must run) before the DEX regions are populated.
- **Tool version sensitivity:** adb is NOT on PATH in this environment even though tool_discover.py reports it 'available' -- it lives at %LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe. Same for aapt/aapt2/dexdump/apksigner/zipalign in %LOCALAPPDATA%\Android\Sdk\build-tools\35.0.0. apktool is a bare jar at C:/Users/F A H A D/Documents/Default Project/tools/apktool.jar invoked as 'java -jar', not an executable. `adb shell` runs everything through /system/bin/sh, so PowerShell $(...) interpolation must be escaped or the command is evaluated on the host.
- **New indicators discovered:** [anon:dalvik-DEX data] regions in /proc/<pid>/maps = in-memory payload (Chiko/NeoArk), /data/data/<pkg> file count unchanged after launch = loader writes no dex to disk, exactly one 'dex\n' magic per anon DEX region, at offset 0, no Application subclass anywhere in the recovered dex => delete the packer's manifest android:name, libfping.so is app-owned, libchikoStub.so is packer-owned
- **Refined applicability for technique:** This is now the complete, documented method for Chiko/NeoArk. The two phases compose: the offline 64-byte XOR path (EXP-0002) recovers the primary blob with no device at all, and the memory-harvest path (this experiment) recovers everything including the blobs whose per-blob keys are not derivable statistically. Together they cover the packer end to end, and the memory path alone is sufficient when a rooted device is available.
